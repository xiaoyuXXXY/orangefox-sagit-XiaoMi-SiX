# 扩容方案 · 从原理到脚本

把小米 6 的 `system` 从原厂 5 GB 扩到 5–12 GB，`data` 相应减少。全部逻辑在
`device/xiaomi/sagit/recovery/root/sbin/fox_resize_system.sh`（601 行），界面上只是调用它。

> **破坏性**：`system` / `cust` / `data` 三个分区会被删除重建并格式化。执行前必须备份，执行后必须重刷 ROM。

---

## 1. 为什么不能「原地扩大」

原厂布局（简化）：

```
sde（另一块 LUN）: system 5 GiB   cust 832 MiB
sda（主盘）      : ... cache ...  userdata  ≈ 52 GiB
```

`system` 和 `userdata` 根本不在同一块盘上，GPT 里的分区也不连续 —— 没有「把 system 的结束扇区往后推」这种操作。唯一可行的办法是：

**在 data 所在的盘上，从 cache 之后重新切一块地，把 system / cust / data 依次重排。**

```
改之前  sda: [ ... ][cache][        userdata 52 GiB        ]
改之后  sda: [ ... ][cache][system N GB][cust 832M][data 剩余 ≈ 8 GB+]
```

代价是 data 变小，而小米 6 的 data 有 50 多 GB，拿出 7 GB 换 system 是划算的。

---

## 2. 容量怎么算

### 公式

```
BASE       = cache 结束扇区 + 1          （没有 cache 则取 First usable sector，兜底 114688）
system     = N GB（N=5 时用 5120 MB，对应原厂）
cust       = 沿用表中现有 cust 的扇区数；取不到或不在 832 MiB–4096 MiB 之间 → 取 832 MiB
data       = 磁盘末尾 - data 起点 + 1
```

全部按 **扇区** 计算（4096 B/扇区），并且**先除后乘**，避免 `8 * 1024 * 1024 * 1024` 这类数在 busybox 的 32 位算术里溢出。

### 约束

| 约束 | 值 | 不满足时 |
|---|---|---|
| data 最小 | 8 GiB | `die`「空间不足」 |
| cust 下限 | 832 MiB | 低于此值 vendor 刷不进去 |
| 新分区编号 | ≥ 16 | 防止覆盖 switch / ssd / bk1 等底层分区 |
| system 扇区数 | > 0 | 内部计算异常则中止 |

### 实测（九档，真机）

| 标称 | system 实际 | data 可用 | 占标称 |
|---|---|---|---|
| 5 GB（原厂） | 5120 MB | 4895 MB | 97.2% |
| 6 GB | 6144 MB | 5887 MB | 95.8% |
| 7 GB | 7168 MB | 6879 MB | 96.0% |
| 8 GB | 8192 MB | 7871 MB | 96.1% |
| 9 GB | 9216 MB | 8863 MB | 96.2% |
| 10 GB | 10240 MB | 9855 MB | 96.2% |
| 11 GB | 11264 MB | 10847 MB | 96.3% |
| 12 GB | 12288 MB | 11839 MB | 96.3% |

每加 1 GB，data 少 1024 MB，文件系统元数据再多占约 32 MB，所以界面上看到的是 **-992 MB**，六次完全一致。

那 3.7% 不是误差：**4Kn 对齐 + ext4/f2fs 元数据是固定开销**，容量算法本身是确定的。

## 3. 脚本流程（12 步）

| 步 | 做什么 | 失败处理 |
|---|---|---|
| 1 | 找 by-name 目录，定位 userdata 与整盘设备 | `exit 1` |
| 2 | `blockdev --getss` 读扇区大小，默认 4096 | 兜底 4096 |
| 3 | `sgdisk --print` 读分区表 | `die` |
| 4 | 取 cache 结束扇区作为 BASE | 兜底 First usable |
| 5 | 收集所有名为 system / cust / userdata 的分区（含历史残留） | `die` |
| 6 | 算新编号 = 剩余分区最大号 +1，小于 16 直接中止 | `die` |
| 7 | 算三个分区扇区数，检查 data ≥ 8 GiB | `die` |
| 8 | `sgdisk --backup` 备份 GPT 到 `/tmp/fox_gpt_backup.bin` | `die`（没备份不写） |
| 9 | 逐个 `--delete`（**一次一个**，精简版 sgdisk 带多个会错位） | `load-backup` 回滚 |
| 10 | 逐个 `--new ... --typecode=8300`（**一次一个**，防 partNum 错位） | `load-backup` 回滚 |
| 11 | **2.5 步**：扫描其它 `sd?`，删掉同名 system / cust | 警告，可忽略 |
| 12 | 校验新表三块齐全 → `rereadpt` → 等节点 → 校验 by-name 指向 → 按设备卸载 → 格式化 | 见下 |

### 为什么要「第 2.5 步」

原厂 system 在 `sde` 上。新 system 建在 `sda` 后，内核里同时存在两个叫 system 的分区，`ueventd` 建 by-name 软链时可能仍指向旧的 —— 结果 ROM 刷进 8 GiB 的新分区，系统却从 5 GiB 的旧分区启动，**怎么刷都不开机**。

所以必须把旧的那份删掉。这也是 V44-15 的核心修复。

### 为什么逐个删、逐个建

镜像里是 AOSP 编出来的精简版 `sgdisk`，一条命令带多个 `--delete` / `--new` 时会按原始编号顺序处理，前面的删除会让后面的编号位移，最后删错分区。逐个执行虽然慢几秒，但编号始终基于最新表。

## 4. 退出码

| 码 | 含义 | 现场状态 | 你该做什么 |
|---|---|---|---|
| 0 | 成功 | 三分区已重建并格式化 | 直接刷 ROM |
| 1 | `die()` 主动停手（参数/空间/读表失败） | **未改动分区表** | 看 `/sdcard/fox_resize_error.txt` |
| 2 | 分区表已写好，但内核没刷新节点 | 分区表 **已改**，data 未格式化 | **重启 Recovery** → 格式化三块 → 刷 ROM |
| 3 | 分区表已写好，格式化有步骤失败 | 分区表 **已改** | 重启 Recovery → 「清除」里逐个格式化 → 刷 ROM |
| 4 | by-name 仍指向旧分区 | 分区表 **已改**，不可刷 ROM | 重启 Recovery → 格式化 → 刷 ROM |
| 5 | 有分区卸不下来 | **未格式化**（前一步已备份回滚） | 重启 Recovery，别在「挂载」页勾任何分区，再试 |

**关键区分**：`exit 3` / `2` / `4` 都是「分区表已经生效，只是收尾没走完」，不要重复扩容，重启后格式化即可。只有 `exit 1` 和 `exit 5` 是真的没动。

---

## 5. 回滚

三个时机各有一次自动回滚，靠的都是第 8 步的 GPT 备份：

- 删除失败 → `sgdisk --load-backup` → `rereadpt`
- 创建失败 → 同上
- 新表校验三块不齐 → 同上

回滚后 **data 保持原样，没有被格式化**，这是最安全的一档失败。

GPT 备份文件在 `/tmp/fox_gpt_backup.bin`（重启后丢失，但那时已经不需要了）。

## 6. 格式化阶段

### 卸载

`/data` 至少被挂三次：`/data`、`/sdcard`、`/storage`（bind mount）。只按挂载点卸会漏，所以：

1. 先按常见挂载点粗卸一遍（`/sdcard` `/storage` `/mnt/runtime/*` …）
2. 再**按设备找挂载点**：`awk '$1==dev {print $2}' /proc/mounts`，逐个 `umount`，最多 5 轮
3. 5 轮后仍挂着 → `exit 5`，宁可不格式化

### 文件系统

- `system` / `cust`：`mke2fs -F -t ext4 -L <label> -m 0`
- `userdata`：
  1. `make_f2fs -f -O encrypt,extra_attr`（4.4 内核能接受的特性）
  2. 失败 → `make_f2fs -f`（默认特性）
  3. 再失败 → `mke2fs ext4`，记 `ACTUAL_FSTYPE=ext4` 并提示降级
- **不传分区大小**给 make_f2fs。让它按整设备自己算，TWRP 那套 `size` 参数在 4K 扇区上会算错（V39 把 112 GB 格成 14 GB 就是这么来的）。

### 重建内部存储

格式化后重新挂载 `/data` → `mkdir -p /data/media/0` → `chown media_rw` → `chmod 0770` → `restorecon`。

漏了这一步，开机后相机、文件管理器会报存储不可用。

## 7. 界面操作

```
主菜单 → 晓宇插件 → 系统工具 → System 分区扩容
  → 选容量（5–12 GB，8 行平铺）
  → 确认页（红字：会清空 Data）
  → 执行（约 1–3 分钟）
  → 完成页：左「重启 Recovery」 / 右「重启系统」
```

**推荐点「重启 Recovery」**，因为格式化后内核分区块设备需要重新枚举。重启后再：

```
清除 → 格式化 Data（此时会问文件系统，选 f2fs）
     → 格式化 System
     → 格式化 Cust
→ 刷 ROM
```

## 8. 两个「看起来是 bug」的现象

### 大跨度扩容报 `exit 3`，但其实成功了

脚本用 `warn()` 累计失败，任何一步失败最后 `exit 3`。5G → 12G 是全程 I/O 峰值（分区表重写 + mke2fs + f2fs 重建），收尾校验偶尔超时被判失败。

**分区表已经写好。** 重启 → 格式化 Data → 正常。属误报，V44-17 之后已让 f2fs 降级不再误判，但极端 I/O 下仍可能出现。

### 12G 刷完不开机

不是扩容坏了，是**刷完没格式化 data**。扩容后 data 是全新分区，旧 f2fs 元数据对不上，卡第一屏一两秒后自动重启。

按顺序「扩容 → 重启 Recovery → 格式化 Data → 刷 ROM」即正常。

## 9. 换到别的机型要改什么

| 常量 | 本项目值 | 怎么定 |
|---|---|---|
| 原厂 system | 5120 MB | `sgdisk --print` 看实际扇区数 × 扇区大小 |
| cust 下限 | 832 MiB | 同上。切小了 vendor 刷不进去 |
| 扇区大小 | 4096 | `blockdev --getss`，不要写死 512 |
| data 最小 | 8 GiB | 按机型 ROM 体积估，太小会装不下 |
| 起点 | cache 结束 +1 | 有的机型没有 cache，用 First usable sector |
| 编号保护 | ≥ 16 | 看底层分区占了多少号，绝不能覆盖 |

另外要确认：`system` 和 `data` 是否在同一块盘上。**不在同一块盘**（像本机原厂）才是这个方案成立的前提；如果本来就在一块盘且 system 后面就是 data，直接 `--change-name` + 调整结束扇区更简单。
